## 3. 合并顺序提案（合入 `feature/product-grade-upgrade`）

原则：每次合并前红队验收；一次只合一个分支；合并后在主工作区重跑全量基线（BASELINE_TESTS 同一套命令）；**在用户本地确认之前，什么都不进 main、不推送。**

| 顺序 | 分支 / 内容 | 理由 | 合并前必须满足 |
|---|---|---|---|
| 1 | `agent/arch-backend`：数据路径环境变量（`RUBBINGMIND_DB_PATH` 等）+ Vite 代理警告，然后 P0（运行排序/legacy、isPassthrough 字段、批次元数据、ID 映射接口） | 先把“测试写进用户真实数据库”的口子堵住，其他分支的测试才能安全隔离；P0 是其他分支的接口前提 | 红队验收：不设变量时 pytest 原样通过；设变量时写入只落指定目录、用户两个 DB 的 SHA 不变；P0 验收标准逐条复现 |
| 2 | `agent/eval-sci`：原图返回/实际处理判据、派生 applied_status、同批复测改名、compare_v21 排除表 | 报告前端要用它的数据口径；`museum_processing.py` 的同一段改动与后端分支保持完全一致，先后合并不冲突（ADR R1-2） | 红队复核 `agent/eval-sci@f21ceaa`（含 experiment_registry.py 改动）；主工作区 `experiments/results` 哈希清单不变 |
| 3 | `agent/jinshi`：C-03、C-02、C-01（`rm:demo:` 命名空间 + `id_mapping.json`）及后续内容修正 | ID 映射的内容依赖后端的映射接口（步骤 1）；史实修正需金石学 + 数据治理审核 | 红队验收；映射关系逐条有人工复核记录；不改 28 件的批准状态、不直接改用户数据库 |
| 4 | `agent/report-frontend`：Phase 1 报告页 | 依赖 1（字段、URL 状态）、2（口径）、3（ID） | 红队验收截图（1920×1080 / 1440×900 / 1366×768 / 390×844）、PDF/JSON/CSV 一致性；首页受保护视觉改动需用户确认截图 |

| 最后 | `feature/product-grade-upgrade` → `main` → 推送 | Phase 6 | **用户在本地确认后才执行**；正常合并，不 force push |
